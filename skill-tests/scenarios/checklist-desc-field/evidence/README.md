# 过程断言的证据

每条过程断言都对应一次**真实发生过的缺陷动作**。这份目录保存那些动作的原始调用记录，
让后来的人能回答「这条规则当初为什么这么写、它解决的是什么问题」。

`runs/` 下的完整运行记录不进版本控制（轨迹里可能有凭据），所以把判据需要的那部分
**脱敏后**留在这里：只有 `calls.ndjson` 里的 `argv` 与 `decision`，
不含轨迹、不含运行目录路径、不含 stdout/stderr。

## 文件命名

```
evidence/<规则标识>-<来源运行>.ndjson
```

- **规则标识**：与 `process.mjs` 里该条断言对应，一眼能对上。
- **来源运行**：`runs/<runId>/` 的 runId，出问题时可以回本机原记录核对（如果还在）。

## 文件内容

与 `calls.ndjson` 同形，一行一条，只保留这两列：

```json
{"argv":["task","create","--items","[\"a\",\"b\"]"],"decision":"allow"}
```

保留**完整的调用序列**而不是只留命中的那几条：绕路要看前后关系，
只截取中间一条会让人看不出「先做了什么、才导致这一步」。

## 加一条过程断言时

1. 从 `runs/<runId>/calls.ndjson` 摘出完整序列，脱敏（删 `at`、`reason`、`targets` 以外的字段）。
2. 存成 `evidence/<规则标识>-<runId>.ndjson`。
3. `process.mjs` 的注释里引用这个文件名，而不是让读者去翻一个可能已被删掉的 runId。
4. `process.test.mjs` 直接读这份文件当夹具——测试与证据同源，不会各自漂移。

## 什么时候删

**规则被删时一起删**——证据是规则的论据，规则不在了留着一份没人解读的日志只会误导。
规则还在、但证据已不成立时，替换成新记录并在注释里写明为什么旧的作废。
