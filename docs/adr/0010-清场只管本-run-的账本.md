# ADR-0010：清场只管本 run 的账本，不检测也不报告别人的任务

- 状态：接受
- 日期：2026-11-09（修订 ADR-0006 的两条约束；0006 的核心规则原样保留）

## 背景

ADR-0006 的核心教训是：**永不清空清单，只删本 run 建的任务**。这条规则不变。

但 0006 同时写了两条附加约束：

> 每次运行前检查测试清单是否为空，不空则拒绝运行并列出可疑任务由用户处置
>
> 清单里出现非本 run 创建的任务时，harness 只报错并停止，不动手

实现 #5 时按这两条做，得到的是：`inspectProjects` 在跑之前扫一遍清单，`planCleanup` 在跑之后扫一遍并比对账本，发现任何未记账任务就 `aborted`，中断后续所有 scenario。

问题在于这两条附加约束引入了一套**本不需要的检测机制**，而它建立在两个错误假设上。

### 错误假设一：断言要扫描清单才能找到任务

`#5` 最初的设想是"结局断言读会话结束后测试清单的最终状态"。如果断言真要靠扫描清单去找"这次运行建的任务"，那清单里混着别人的任务确实会污染判断——所以要先清场。

但 #7 的断言设计改了：**断言从 `created.json` 读 id，再按 id 取那几条任务的终态**。别人的任务在这个模型里根本不在视野内。

### 错误假设二：运行时检测可以兜住代码 bug

"清单里有未记账的任务"这个信号，被当成了安全问题。但实际上它有两个来源：

- 别人的任务（合法，与本次运行无关）
- 本 run 的账本丢了记录（bug）

前者不是错误，后者是代码要修的 bug。**用运行时检测去兜代码 bug，是把测试该干的事塞进生产路径。**

## 决定

**一条 scenario 的全部事实源是 `created.json`。** 断言读它，清场删它。别人的任务不在这个视野里。

具体改动：

1. **删掉 `inspectProjects`**，不再做运行前清单检查。开跑前不扫清单。
2. **`planCleanup` 不再产出 `foreign`**。只按账本逐条匹配，清单里其它任务直接跳过——不检测、不报告。
3. **删除目标取实际枚举到的清单**，不用账本里记的 `projectId`。两者不一致时报 `mismatched`，但仍按实况删（agent 建完后把任务移到别的清单是合法行为）。
4. **清场失败不中断后续 scenario**。账本按 runId 隔离，删不掉自己的那几条不影响下一条的判断。失败记 log，退出码非零。
5. **清场后自查**：删完重读清单，账本里的 id 仍在就报 `remaining`。这是纯自查，不涉及别人的任务。

## 后果

- **并行运行多个 run 现在是安全的**：各自只碰自己的账本。
- 测试清单里可以长期存在用户手动建的任务，不影响任何 scenario 的运行与判断。
- **账本丢记录的错误不再被运行时拦截**。它现在只会表现为"某条任务残留"，需要靠代码正确性保证——`created.json` 因此改成了 NDJSON 追加式（见后果段下方）。
- `created.json` 改名为 `created.ndjson`，一行一条追加写入：并发 create 不互相覆盖，进程被 kill 在写入途中最多留一行残片，读时跳过。

## 考虑过的方案

- **保留运行前检查，放宽为"只警告不阻止"**：仍然要扫一遍清单，仍需区分"别人的任务"与"我的残留"，而这两者在运行时无法可靠区分（残留的定义就是账本里没有）。
- **用标题前缀标记本 run 的任务**：ADR-0006 已否决过按规则扫描的做法，前缀规则写错一样会误删。
- **保留 `foreign` 但只写进报告**：报告里出现别人的任务会让读者误解为"本次运行碰到了它"，实际上是噪音。

## 与 ADR-0006 的关系

0006 的两条附加约束作废，核心规则保留并加强：

> **harness 永不清空清单。** 它创建的每一条任务在创建后立刻记入账本，清理时只删该账本里记录的 id。不做任何形式的按清单扫描删除。

新模型下这条规则更强了——不是"扫描后判断该不该删"，而是"只认账本，压根不扫描"。
