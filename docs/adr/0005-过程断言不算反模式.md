# ADR-0005：过程断言不违反"勿断言调用顺序"

- 状态：接受
- 日期：2026-11-06

## 背景

`tdd` skill 的 `tests.md` 把"断言调用次数/顺序"列为反模式，理由是这类测试与实现耦合，重构未改行为时也会失效。

本项目的 scenario 恰恰要看调用序列：缺陷不只表现为结局错误，也表现为"结局侥幸正确但过程中绕远路"。例如先建一个 `CHECKLIST` 任务、发现正文不显示、再删掉重建为 `TEXT`——最终状态完全正确，但这次会话的 skill 引导是失败的。

## 决定

**过程断言合法，但只写已确认的硬规则。** 判定依据是调用序列，不覆盖"用了什么巧妙的替代做法"这类主观判断。当前只允许三类：

1. 不存在"创建带 `--items` 的任务后删除重建"的序列；
2. 不存在"`content` 从非空变为空"的更新；
3. 不存在目标清单不在测试清单集合内的写调用。

质量维度（绕路、冗余操作、是否先读后改）交由判定 agent 写进报告，**不影响通过或失败**。

## 理由

`tdd` 那条反模式的前提是"存在一层被绕过的实现细节"。本项目没有这一层：被测对象是 skill 文档，agent 的工具调用轨迹就是它的公开行为，不存在"重构后行为不变但调用序列变"的情形——调用序列变化本身就是行为变化。

## 后果

- 过程断言是判定链的第三面：只有可信度检查与结局断言都通过才判（见 ADR-0014）。结局断言不过即终止，过程断言不执行——没做到的话，谈有没有绕远路没有意义。
- 新增过程规则前，必须有一次真实会话证明该规则对应已确认的缺陷，否则容易演变成给模型写剧本，把"更聪明的替代做法"误判为失败。

## 补充（2026-11-18，实现 #8 时）：规则表凭证据准入，越界写入不进判定

「决定」一节写「当前只允许三类」，读起来像一份封闭清单；实现 #8 时确认这条措辞要改，并且第 3 条要移出判定。

### 规则表是凭证据准入的，不是三类

规则不凭缺陷描述反推，也不在设计时预先写定。它的来源是**一次真实运行暴露出来的缺陷动作**：判定 agent 在报告里指出「绕路了」，人确认这是真缺陷，再把它沉淀成一条可判的规则，`discoveredBy` 指向暴露它的那条 scenario。

所以「三类」不是上限，是当时已知的存量。正确说法是：**过程断言是一张凭证据准入的全局规则表**，条目随真实运行增长；新增一条的前提是有一次真实会话证明它对应已确认的缺陷（本 ADR 原文最后一节已写）。

**实现时这张表是空的。** 原文的规则 1（建带 `--items` 的任务后删除重建）有来源缺陷描述，但没有它真实发生过的会话记录；规则 2（`content` 从非空变空）手里只有反证——`docs/specs/dida-cli-skill-评测平台.md` 的「先行验证过的事实」写了两遍 `update --items` **不会**清空 `content`，事实核验阶段也判定「更新会清空正文」不成立。仓库里只有一条 scenario，还没有任何一次真实运行提供证据，因此两条都未登记。**规则等用例跑出证据再进表，不预先占位。**

`PROCESS_RULES` 为空的运行，第三面一条不判，结论与加这条机制之前一致。

### 越界写入移出过程断言，改为报告单列

原文规则 3「不存在目标清单不在测试清单集合内的写调用」实现时是**被 shim 当场拦住**的——写请求根本没发出去，保护层是生效的。它的信号含义是「agent 试图越界写」，而不是「skill 没做到」，而归因有四种来源：

| 来源 | 该怪谁 |
|---|---|
| agent 用错命令（漏 `--project`、写错清单 id） | skill 没讲清 |
| skill 示例里的默认清单不适用于本 scenario，原话又没点名 | **scenario 设置错** |
| 命令确实需要，但 guard 的 `WRITE_COMMANDS` 没覆盖 | **guard 不完善** |
| 真绕过意图 | 应当拦住 |

后两类判成 `failed` 是假红，而 ADR-0014 的整个动机就是消除「红得不对」的信号。因此越界写入**只进报告**（按 `reason` 分开计数），不进 pass/fail。

这条也说明过程断言与可信度检查不是同一类信号：可信度检查判的是「调用有没有走过 shim」，越界写入判的是「走过 shim 的调用被拦了」——后者不涉及事实是否可信，只涉及动作是否越界，而越界的原因无法从日志判定。

### 后果

- 过程断言这一面在规则表为空时不产出任何结论；报告里「过程断言 通过（N 条规则）」只在 N > 0 时出现。
- 规则的 `discoveredBy` 指向的 scenario 被删掉或改名后，全量运行在汇总末尾提醒「规则失去了当初的证据」，不改变退出码——它说明流程没走完，与 `probes/` 残留提醒同类。
- 规则的本体是我们自己的代码：判 `broken`（去修 harness），不判 `failed`（去改 skill）。
- 原文的「只允许三类」与第 3 条按修订惯例保留原貌，读者以本段为准。
