# ADR-0005：过程断言不违反"勿断言调用顺序"

- 状态：接受
- 日期：2026-11-06

## 背景

`tdd` skill 的 `tests.md` 把"断言调用次数/顺序"列为反模式，理由是这类测试与实现耦合，重构未改行为时也会失效。

本项目的 scenario 恰恰要看调用序列：缺陷不只表现为结局错误，也表现为"结局侥幸正确但过程中绕远路"。例如先建一个 `CHECKLIST` 任务、发现正文不显示、再删掉重建为 `TEXT`——最终状态完全正确，但这次会话的 skill 引导是失败的。

## 决定

**过程断言合法，但只写已确认的硬规则。** 判定依据是调用序列，不覆盖"用了什么巧妙的替代做法"这类主观判断。当前只允许三类：

1. 不存在"创建带 `--items` 的任务后删除重建"的序列；
2. 不存在"`content` 从非空变为空"的更新；
3. 不存在目标清单不在测试清单集合内的写调用。

质量维度（绕路、冗余操作、是否先读后改）交由判定 agent 写进报告，**不影响通过或失败**。

## 理由

`tdd` 那条反模式的前提是"存在一层被绕过的实现细节"。本项目没有这一层：被测对象是 skill 文档，agent 的工具调用轨迹就是它的公开行为，不存在"重构后行为不变但调用序列变"的情形——调用序列变化本身就是行为变化。

## 后果

- 过程断言是判定链的第三面：只有可信度检查与结局断言都通过才判（见 ADR-0014）。结局断言不过即终止，过程断言不执行——没做到的话，谈有没有绕远路没有意义。
- 新增过程规则前，必须有一次真实会话证明该规则对应已确认的缺陷，否则容易演变成给模型写剧本，把"更聪明的替代做法"误判为失败。

## 补充（2026-11-18，实现 #8 时）：规则按 scenario 写、缺省允许，越界写入不进判定

「决定」一节写「当前只允许三类」，读起来像一份封闭清单；实现 #8 时确认这条措辞要改，第 3 条要移出判定，而且规则不该集中在一张全局表里。

### 规则按 scenario 写，与结局断言对称

过程断言写成 `scenarios/<id>/process.mjs`，形状与 `assert.mjs` 相同：默认导出一个函数，收 `{ calls }`（**只有调用日志**——轨迹归可信度检查、终态快照归结局断言），返回 `{ok, name, expected, actual}[]`。

**不设全局规则表，也不设共享规则库。** 曾按「harness 全局三条」实现过一版（每条规则带 `discoveredBy` 指向来源用例、全量运行检查来源是否还在），被否掉的理由是：那样一来「过程断言」的产出变成了「规则库里的规则都过了」，而它本该回答的是「**这条 scenario 的过程对不对**」。判据散在别处，看一条用例的文件时看不出它要求的过程是什么；为了复用而拆散规则，会把「把这条用例的过程写正确」这件事掩盖掉。

因此复用的代价是明写出来的：

- 同一个缺陷在几条用例都相关时，规则要各写一份。**这是用重复换可读性**，接受。
- A 用例发现的缺陷，B 用例不会自动被检查。B 没写就是不判——那是 B 作者的选择，不是静默遗漏。

### 缺省允许，但「未判」不能冒充「通过」

`process.mjs` 是可选的。没写时这条用例不判过程这一面，结论记为 `passed` 且 `process.evaluated: false`，报告写「过程断言 未判（这条用例没有 `process.mjs`）」，**不写「通过」**。没做的事不能说成做了。

这与 `assert.mjs` 缺省即报配置错误不同：结局断言是每条 scenario 的必备项（没有它就没有判据），过程断言只覆盖已确认的过程缺陷，一条用例未必有。

### 写过程断言要先看记录

过程断言的判据不能凭想象写。按本 ADR 的准入条款，写之前必须有一次真实会话的调用记录讲清两件事：

1. **正确步骤是什么**——这条用例的意图对应哪几步 dida 调用；
2. **哪些动作是错的**——记录里实际出现了、且已确认属于缺陷的动作。

没有记录作依据，写出来的规则要么抓不到真问题，要么把合理路径判红。规则本身只写「禁止什么」，不写「必须按某个顺序做」——后者是给模型写剧本（本 ADR 原文的后果段已写）。

### 越界写入移出过程断言，改为报告单列

原文规则 3「不存在目标清单不在测试清单集合内的写调用」实现时是**被 shim 当场拦住**的——写请求根本没发出去，防护是生效的。它的信号含义是「agent 试图越界写」，不是「skill 没做到」，而归因有四种来源：

| 来源 | 该怪谁 |
|---|---|
| agent 用错命令（漏 `--project`、写错清单 id） | skill 没讲清 |
| skill 示例里的默认清单不适用于本 scenario，原话又没点名 | **scenario 设置错** |
| 命令确实需要，但 guard 的 `WRITE_COMMANDS` 没覆盖 | **guard 不完善** |
| 真绕过意图 | 应当拦住 |

后两类判成 `failed` 是假红，而 ADR-0014 的整个动机就是消除「红得不对」的信号。因此越界写入**只进报告**，按 `reason` 逐项计数（越界写入 / 未知命令 / id 不一致 / 解析不出目标），不进 pass/fail。

这条也说明过程断言与可信度检查不是同一类信号：可信度检查判的是「调用有没有走过 shim」，越界写入判的是「走过 shim 的调用被拦了」——后者不涉及事实是否可信，只涉及动作是否越界，而越界的原因无法从日志判定。

### 后果

- 原文的「只允许三类」与第 3 条按修订惯例保留原貌，读者以本段为准。
- 全局规则表方案（`harness/lib/processassert.mjs`、`discoveredBy` 来源提醒）在本补充定稿前的实现里存在过，已随本决定删除；如需追溯，看提交 5758c69。
- `process.mjs` 抛异常或返回非法形状判 `broken`，报告的标题指向该用例的 `process.mjs`，与 `assert.mjs` 坏掉分开。
