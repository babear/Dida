# ADR-0014：三面判定改为严格顺序短路，会话正常结束是前置门

- 状态：接受
- 日期：2026-11-16

## 背景

ADR-0012 把判定拆成三面（可信度检查 → 过程断言 → 结局断言），并写「任一面红即停」。实现 #33 时这句话被读成「不评估」：`decideAssertion` 在可信度检查不通过时早退，断言模块从不被调用。随后同一个 PR 又把它改成「评估与判定分开」——每一面只要事实存在就算，结论留在 `evaluated` 里，只有 status 由第一个红的面决定。ADR-0012 第 133–143 行把这条写成了通则。

这条通则的代价在真实使用里暴露出来：一次被可信度检查挡下的运行，报告里会同时出现「结果不可信」和「结局断言未通过」两组结论。**两组结论并存时，读者无法判断后者该不该信**——而可信度检查的判据至今仍是「比条数」（#18），分不清「真的绕过 shim」与「agent 只是做了次文件操作」。把可能失真的结论和真红并排放在一起，等于把判断责任推给读者。

维护者的判断是：**一次运行只该给出一个结论。** 前面那一面没过，就说明这次运行的事实基础不成立，后面各面算出来的东西没有参考价值，不该算，更不该写进报告。

## 决定

### 会话正常结束是前置门，不属于三面

三面判定说的是「会话跑完之后怎么判」。会话没正常结束（退出码非 0 或超时）时，判定链**根本没有开始**：不取快照、不跑任何断言。这与 ADR-0012 第 143 行「会话没正常结束时也先判可信度」相反，那句作废。

理由是顺序性的：一张「会话未正常结束」的报告已经说明这次运行没有产出可判的事实，再去判调用日志可不可信没有意义。

### 三面改为严格顺序，前一面不过就不算后面

```
会话正常结束？  否 → incomplete，判定链未开始
      ↓ 是
可信度检查      不过 → invalid，不取快照、不跑断言
      ↓ 通过
取快照 ＋ 结局断言   快照取不到 → invalid（cause: state）
                    断言不过 → failed / broken
      ↓ 通过
过程断言        不过 → failed
      ↓ 全过
   passed
```

顺序是 **可信度检查 → 结局断言 → 过程断言**。与 ADR-0012 的三面表（过程在中间）**相反，这是有意调整**：结局断言问「做到了没有」，过程断言问「怎么做到的」。没做到的话，谈有没有绕远路没有意义。

「评估」这个概念取消。不再有「算了但不计入判定」的结论，`evaluated` 字段与其全部渲染路径删除。报告里只出现第一个红的面。

### 快照在结局断言那一刻取，不在会话结束时取

终态快照的唯一用途是给结局断言读。它必须在清场之前取（清场删的正是这些任务），此外没有别的顺序约束。

把取快照挪到可信度检查之后，省掉可信度失败那些运行的一次清单枚举。取不到快照时判 `invalid`（cause: `state`）并停在这里——那是基础设施故障，不是 skill 没做到，写成 `failed` 会把人引向错误的方向。

### 清场永远最后，且只在全过时执行

停的是判定，不是收尾。清场放在判定链之后，但**只有 `passed` 才执行清场**。以下情形一律保留现场：

| 结果 | 清场 | 理由 |
|---|---|---|
| `passed` | 执行 | 没有现场要留 |
| `incomplete`（会话没正常结束） | 保留 | agent 可能只干到一半 |
| `invalid`（可信度失败） | 保留 | 账本只能覆盖走过 shim 的调用，绕过建的任务清不掉；留现场比清一半好查 |
| `failed` / `broken`（任一断言面不过） | 保留 | 要能对着任务清单看断言为什么失败 |

这与现状相反：现在的门控是「会话没正常结束才不清场」，断言失败照清。

保留现场的两种情形，报告与控制台都要写「现场已保留，用 `--clean <runId>` 收尾」。批跑结束时另外汇总列出这些 run——失败即留现场，跑十条挂六条就是六批任务，没有清单会让人下次打开客户端时无从追溯。

### 状态名对外统一

内部状态、控制台标签、报告措辞三者用同一个词。`skipped` / `INCOMPLETE` / 「未正常结束」三套说法并存会让人问「跳过什么了、谁跳过谁」——实际发生的是**前置门没通过，判定链没开始**，用 `incomplete` 一个词表达。

## 被否掉的替代方案

**保留「评估不停、判定短路」（#34 的方案）。** 被否的理由不是它错，而是它把结论的可信度问题留给了读者。要想让它成立，得先让可信度判据能区分「真绕过」与「文件操作」（#18），并且报告要能给每组结论标注可信等级——那是另一套更复杂的机制。既然判据短期改不动，就选一个不依赖判据精度的形状。

**只改顺序、保留评估分离。** 同样被否：两者在「报告里是否出现多组结论」这件事上没有区别。

## 后果

- **可信度检查的误报代价被放大到最大。** 判据仍是「比条数」，而工具面没有 Bash，agent 做任何文件操作都必须走 PowerShell——一次 `Get-ChildItem` 就足以让整条运行既无快照也无任何断言结论。ADR-0012 第 139 行描述的那个场景在新形状下从「偶尔」变成「必然」。因此 **#18 必须在第一条真实 scenario 落地前修掉**，否则回归网会在第一次真实使用时就失去全部信号。这是本 ADR 最重要的后果。
- 报告层删掉 `evaluatedBlock` 与「同一份终态的结局断言（不影响上面的结论）」整节；控制台删掉对应段；`decideAssertion` 不再返回 `evaluated`。相关测试需整组重写。
- 失败即留现场，意味着失败运行会在真实测试清单里留下任务，需要人用 `--clean` 收尾。批跑汇总必须列出这些 run。
- ADR-0012 的三面表、判定顺序代码块、「评估与判定是两件事」整段需要按本 ADR 改写；ADR-0005 第 28 行「过程断言必须与结局断言共同决定结果」需要改成「结局断言通过后才判过程断言」。
- `probes/` 与 `scenarios/` 是两条独立流程：探针不参与判定，因此不受本 ADR 的判定链与清场门控约束。
