# dida-cli skill 行为评测平台

## Problem Statement

`dida-cli` skill 的三份文档（`SKILL.md`、`references/task.md`、`references/project.md`）从未被验证过。2026-11-05 的一份使用反馈记录了六条缺陷：`--items` 的 JSON 格式不可用、`CHECKLIST` 任务的正文在客户端不渲染、带 `--items` 的更新疑似清空正文、`kind` 无法回退、网络失败信息不区分阶段、`--json` 模式下错误混入纯文本与 Node 堆栈。

这些缺陷里，只有一部分能靠改 skill 文档解决，其余属于 `dida` 二进制本身的行为边界。而"改完之后到底有没有解决"目前无法回答：没有可执行的测试，每次改动只能靠重新做一遍真实操作来肉眼确认，且无法防止以后的改动把已修好的行为改坏。

同时，`~/.claude/skills/dida-cli` 是指向主仓库的软链接，不是当前 worktree。直接在全局环境里试，测的永远不是正在改的那份。

## Solution

一个本地运行的评测 harness：每条 scenario 启动一个全新的一次性 `claude -p` 子进程，只加载沙箱里的那一份 skill，用用户原话驱动它真实调用 `dida` 把任务写进测试清单，会话结束后读测试清单的最终状态和调用序列做断言。

修改 skill 之前先跑一次，断言必须失败——这是复现价。改完再跑，断言必须通过。全量跑一遍就是回归网。

agent 接触不到断言、期望行为和反馈原文。写入被 shim 限制在测试清单内，越界写入根本发不出去。

## User Stories

1. 作为 skill 维护者，我想要一条命令跑完全部 scenario，以便在一次改动后确认没有改坏已修复的行为。
2. 作为 skill 维护者，我想要只跑一条 scenario，以便在 TDD 内循环里快速验证当前这一处改动。
3. 作为 skill 维护者，我想要修改前的基线运行必定失败，以便确认这条 scenario 真的能复现缺陷，而不是一条永远绿的假测试。
4. 作为 skill 维护者，我想要测试报告记录本次加载的 skill 内容指纹与 git rev，以便事后确认测的是哪一份 skill。
5. 作为 skill 维护者，我想要测试报告记录解析到的真实模型，以便模型换代后能判断历史结果是否可比。
6. 作为 skill 维护者，我想要被测 agent 只能看到用户原话和素材文件，以便测试结果反映真实用户场景而非我预先埋好的提示。
7. 作为 skill 维护者，我想要被测 agent 的工具面被限制为 `Skill`、`PowerShell`、`Read`、`Glob`、`Grep`、`Write`，以便它不能用 `WebFetch` 去查文档来绕过 skill。
8. 作为 skill 维护者，我想要每次会话在全新沙箱里运行，以便上一次的残留文件不会影响这一次。
9. 作为 skill 维护者，我想要沙箱里的 skill 是当前工作目录的那一份，以便在 worktree 里改的代码真的被测到。
10. 作为 skill 维护者，我想要沙箱只继承认证相关的环境变量，以便个人偏好（模型选择器、语言、更新器开关）不混进被测环境。
11. 作为 skill 维护者，我想要所有写入被限制在测试清单内，以便真实数据不会被误改。
12. 作为 skill 维护者，我想要越界写入被 shim 当场拒绝而不是事后发现，以便测试环境是安全的而不是靠信任。
13. 作为 skill 维护者，我想要被拒绝的调用留下记录，以便我知道 agent 曾经试图越界。
14. 作为 skill 维护者，我想要 harness 只删除自己创建的任务，以便清单里其他人建的数据不会被清掉。
15. 作为 skill 维护者，我想要运行前检查测试清单是否为空，以便残留数据不会污染本次结果。
16. 作为 skill 维护者，我想要失败的运行保留现场，以便我能回看 agent 到底做了什么。
17. 作为 skill 维护者，我想要一个显式的清理命令，以便确认完现场后一次性收尾。
18. 作为 skill 维护者，我想要会话的完整轨迹被原样保存，以便以后断言逻辑改了还能用同一份事实重放。
19. 作为 skill 维护者，我想要从 shim 拿到解析后的 argv 数组而非命令字符串，以便过程断言不用重新解析引号和转义。
20. 作为 skill 维护者，我想要结局断言和过程断言共同决定通过或失败，以便"结局对了但绕远路"也算失败。
21. 作为 skill 维护者，我想要过程断言只覆盖已确认的硬规则，以便"用了别的聪明做法"不会被误判。
22. 作为 skill 维护者，我想要判定 agent 对轨迹给出质量评价，以便看出绕路、冗余操作、没有先读后改这类问题。
23. 作为 skill 维护者，我想要判定 agent 不影响通过或失败，以便红绿信号不会随措辞漂移。
24. 作为 skill 维护者，我想要首次失败时自动重试一次，以便模型抽样波动不会淹没真实回归。
25. 作为 skill 维护者，我想要报告区分"正常完成"和"完成了但费劲"，以便从测试里读出 skill 质量的趋势。
26. 作为 skill 维护者，我想要每条 scenario 的成本与轮数被记录，以便发现异常昂贵的会话。
27. 作为 skill 维护者，我想要被杀的会话被判为"未收敛"而不是"失败"，以便诊断结论不被混淆。
28. 作为 skill 维护者，我想要 `npm test` 直接跑全量，以便 `/implement` 的"full test suite"自动命中。
29. 作为 skill 维护者，我想要 `/tdd` 写红测试时先加 scenario 再跑它，以便红绿循环和现有工作流一致。
30. 作为 skill 维护者，我想要 scenario 的断言基于实测行为而非反馈原文的描述，以便断言不会建立在不成立的前提上。
31. 作为 skill 维护者，我想要 harness 有探针模式，以便新增 scenario 时能先拿到真实行为样本再写断言。
32. 作为 skill 维护者，我想要一个人工复核清单，以便验证"客户端是否渲染正文"这类无法自动化的判断。
33. 作为 skill 维护者，我想要网络失败的 scenario，以便验证 skill 是否教 agent 正确处理不可重试的错误。
34. 作为 skill 维护者，我想要测试清单里出现非本 run 创建的任务时 harness 停下来，以便我手动处置而不是被自动删掉。
35. 作为 skill 维护者，我想要硬规则：清场永不按清单扫描删除，以便这次误删他人任务的事故不会重演。

## Implementation Decisions

### 结构

harness 是仓库根目录下的一个 Node 模块目录，入口是一个可执行脚本，无第三方框架依赖。

- 编排器：串联清场检查 → 建沙箱 → 起会话 → 断言 → 出报告
- 沙箱模块：建临时目录、复制 skill、算指纹、生成配置
- 会话模块：拼装并启动 `claude -p`、清理继承的环境变量、解析 NDJSON
- 断言模块：结局断言与过程断言
- 判定模块：起判定 agent、写质量报告
- shim：`dida.cmd` + 一个 Node 脚本承担判定与记账

### 三层名词

工具面、shell、可执行形态是三件不同的事，不可互相替代：

- **工具面**是被测 agent 可调用的 tool 名集合。本机没有 `Bash` 工具，执行命令的唯一工具是 `PowerShell`（实测其内部运行 `pwsh.exe` 7）。
- **shell** 是 `pwsh`、`cmd`、`bash` 这些解释器，agent 只能在 `PowerShell` 工具内部再调起它们，不存在"改用 cmd 工具"这回事。
- **可执行形态**是同一命令的不同文件（`dida.cmd` / `dida.ps1` / 无后缀 `dida`）。shim 的形态选 `.cmd`，判据见 ADR-0004。

### 会话启动契约

- 用 `--agents` 加载一份工具面受限的 agent 定义，用 `--agent` 选中它。实测 `--agent` 与 `--tools` 都能限制工具，选 `--agents` 是因为定义是仓库里的文件，有 diff、能 review、能回滚，且开机成本更低。
- 必须同时传 `--allowedTools`。实测只给 `--agents` 限制工具而不给 `--allowedTools`，所有命令都会被 `dontAsk` 模式拒绝。
- 必须重定向 stdin（`< /dev/null`）。实测 stdin 未关闭时 `claude -p` 会等待输入并挂死，表现为超时且无任何 `result` 输出。
- 输出用 `--output-format stream-json --verbose`，`--no-session-persistence` 避免落在用户目录。
- 权限模式用 `dontAsk`。

### 隔离

- 沙箱是每次运行新建的临时目录（`%TEMP%/run-<id>/`），含 `.claude/skills/dida-cli/`（从 `--skill-path` 复制）、素材文件、只含 `ANTHROPIC_*` 键的 `settings.json`、以及 `bin/dida.cmd`。
- 会话以沙箱目录为 `cwd`、以 `CLAUDE_CONFIG_DIR` 指向沙箱配置目录启动，并清除从父进程继承的全部以 `CLAUDE` 开头的环境变量（含无下划线的 `CLAUDECODE`）。CLI 自身注入的 `CLAUDECODE`、`CLAUDE_CODE_SESSION_ID` 等变量不受此控制，见 ADR-0008 的后果段。
- 沙箱**不放仓库内**：实测放在仓库子目录会继承父目录的 `CLAUDE.md` 与父目录 `.claude/skills/` 下的 skill，后者的同名 skill 会与沙箱副本竞争。`CLAUDE_CODE_DISABLE_CLAUDE_MDS` 只阻断自动加载，agent 主动 `Read` 仍能读到父目录的 `CLAUDE.md`。
- 沙箱路径写入 manifest 并打印在报告首行；运行失败时不删除沙箱，便于回看现场。
- **沙箱只隔离工作目录，不隔离文件系统**：agent 仍可用绝对路径读取沙箱外的任何文件。已知风险与失效的缓解手段记在单独的 issue。
- 不适用 `--bare`：它的认证只认 `ANTHROPIC_API_KEY` 或 apiKeyHelper，而本机认证是本地代理；且它会让 hooks 失效、不把 skill 列表暴露给模型。

### shim 规则

单份 `dida.cmd`，记账后原样转发给真 `dida.cmd`，退出码透传。

目标清单的解析规则：`task create` / `task update` 取 `--project`；`task move` 取 `--from` 与 `--to`；其余写命令取位置参数中的 projectId。所有解析出的目标必须 ∈ 测试清单集合。

拒绝时输出与真 CLI 同构的 API 错误文本与退出码 1，不暴露测试机制。转发时吞掉真 CLI 在错误路径上打出的 Node 断言行。

`task create` 与 `task update` 的 `--project` 都是必填参数（实测省略会报 `required option`），因此"漏传导致写进收集箱"不构成风险，只需判定显式传入的值。

### 测试清单

`Test_1` 与 `Test_2` 两个清单，id 由环境变量注入。当前两者均为空。

### 报告

每次运行产出：manifest（skill 指纹、git rev、沙箱绝对路径、三层模型信息、成本、轮数）、原始轨迹、调用日志、断言结果、质量报告、人工复核表。

产物写在仓库根的 `runs/` 下，`runs/` 进 `.gitignore`。运行失败时保留沙箱与产物不删，成功时按保留策略清理旧的。

通过或失败只由断言结果决定，质量报告不影响退出码。

### 模型记录

记录三层并标注可信度：CLI 自报的别名、从 `ANTHROPIC_DEFAULT_*` 读到的真实映射、代理地址。CLI 自报的模型名是别名，不可作为实际执行的模型凭据。

### 护栏

`--max-turns` 在本机 CLI 上被接受但无效，轮数限制必须由 harness 侧看门狗实现，超出阈值直接杀进程树并判"未收敛"。`--max-budget-usd` 是硬中断但会超支约一个调用，且中转账单与本地估算存在出入，只作量级参考。护栏是第二阶段的事。

## Testing Decisions

### 什么是好测试

只测外部行为：会话结束后测试清单的实际状态，以及这次会话真实发生过的调用。不断言 harness 内部实现，不断言 skill 文件的具体措辞——改写法不该让测试失败，改行为才该。

### 唯一接缝

一条 scenario 的接缝是**一次完整的 agent 会话**。所有断言都从两个事实源读取：会话结束后测试清单的最终状态，以及该会话的调用日志。

不建 CLI 层的独立接缝：那里的断言测的是 npm 包，改 skill 永远不会让它变绿。不建 shim 层的接缝：它是基础设施，不是被测对象。

### 断言构成

- 结局断言：测试清单最终状态的字段判断
- 过程断言：调用序列上的硬规则，当前只有三类（不得先建 `CHECKLIST` 再删掉重建、不得让 `content` 从非空变空、不得有越界写入）

两者共同决定通过或失败。

### scenario 的取材

新增 scenario 必须先在探针模式下跑一次真实会话，拿到事实样本后写断言。不得从缺陷报告的文字描述直接反推断言——事实核验阶段已经发现，报告中"更新会清空正文"这条在当前版本上不成立。

### 先行验证过的事实

事实核验阶段以真实调用确认了以下行为，scenario 的断言以此为准：

- `--items '["A","B","C"]'`（字符串数组）会逐项被丢弃并告警，任务落成 `TEXT` 且 `items` 为空；只有对象数组 `[{"title":"A","status":0}]` 或逗号分隔才生效
- 用对象数组建成的任务 `kind` 为 `CHECKLIST`，同时 `content` 可以非空——数据存在但客户端不渲染
- `update --items` **不会**清空 `content`
- `update --items ""` 完全无效，`items` 保留，`kind` 无法回退
- `task get --json` 遇 404 时 stdout 为空，错误以纯文本落在 stderr，进程以非零退出码崩溃
- 只写 `--content` 建成 `TEXT`，再用 `--parent-id` 建子任务，父任务保持 `TEXT`、`content` 不变、`childIds` 正确

## Out of Scope

- 修改 `dida` 二进制本身。它不在本仓库，六条缺陷中的 CLI 层问题只能通过 skill 文档规避，无法修复。
- 自动验证滴答客户端的渲染结果。客户端不提供可编程接口，只能靠人工复核表。
- 跨平台支持。harness 绑定当前 Windows 环境的具体行为（`PowerShell` 工具、`.cmd` 形态、无 OS sandbox）。
- 通过网络层面模拟 `fetch failed`。shim 可以注入该故障，但属于第二阶段。
- 轮数看门狗与预算护栏。已确认 `--max-turns` 无效、预算护栏会超支且金额不可信，具体实现留到第二阶段。
- 判定 agent 的评分纳入通过标准。它只写报告。
- 在 CI 中运行。会话成本与对本地登录态的依赖决定了它只能在维护者本机跑。

## Further Notes

- 一次极短会话的固定成本约 $0.03–0.09（系统提示与工具定义的开销），14 轮文件操作约 $0.29。工具面收窄能显著降低成本。成本数字来自本地估算，中转账单可能不同。
- `~/.claude/settings.json` 把四个模型别名全部映射到中转站的 `deepseek-v4.1-flash` 系列，因此 CLI 报告的模型名与实际执行的模型不是一回事。
- 事实核验期间发生过一次数据事故：清理探针任务时按清单全量删除，误删了用户手动创建的一条任务，且 Open API 无回收站可恢复。这条事故直接产生了 ADR-0006 与第 14、15、34、35 条用户故事。
- 相关决策见 `docs/adr/0003` 至 `0008`。
