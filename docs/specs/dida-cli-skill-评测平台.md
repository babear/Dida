# dida-cli skill 行为评测平台

## Problem Statement

`dida-cli` skill 的三份文档（`SKILL.md`、`references/task.md`、`references/project.md`）从未被验证过。2026-11-05 的一份使用反馈记录了六条缺陷：`--items` 的 JSON 格式不可用、`CHECKLIST` 任务的正文在客户端不渲染、带 `--items` 的更新疑似清空正文、`kind` 无法回退、网络失败信息不区分阶段、`--json` 模式下错误混入纯文本与 Node 堆栈。

这些缺陷里，只有一部分能靠改 skill 文档解决，其余属于 `dida` 二进制本身的行为边界。而"改完之后到底有没有解决"目前无法回答：没有可执行的测试，每次改动只能靠重新做一遍真实操作来肉眼确认，且无法防止以后的改动把已修好的行为改坏。

同时，`~/.claude/skills/dida-cli` 是指向主仓库的软链接，不是当前 worktree。直接在全局环境里试，测的永远不是正在改的那份。

## Solution

一个本地运行的评测 harness：每条 scenario 启动一个全新的一次性 `claude -p` 子进程，只加载沙箱里的那一份 skill，用用户原话驱动它真实调用 `dida` 把任务写进测试清单，会话结束后读测试清单的最终状态和调用序列做判断。

修改 skill 之前先跑一次，断言必须失败——这是复现价。改完再跑，断言必须通过。全量跑一遍就是回归网。

被测 agent 接触不到断言、期望行为和反馈原文。写入被 shim 限制在测试清单内，越界写入根本发不出去。

**一条 scenario 由四部分组成**：用户原话、沙箱素材、可选的预设、断言。原话与素材是给被测 agent 的全部输入；预设是会话前造出前置数据的命令；断言是会话后的判断依据。

判定分三面，按顺序短路：**可信度检查 → 过程断言 → 结局断言**。任一面红即停，退出码非零，报告写明是哪一面。

## User Stories

1. 作为 skill 维护者，我想要一条命令跑完全部 scenario，以便在一次改动后确认没有改坏已修复的行为。
2. 作为 skill 维护者，我想要只跑一条 scenario，以便在 TDD 内循环里快速验证当前这一处改动。
3. 作为 skill 维护者，我想要修改前的基线运行必定失败，以便确认这条 scenario 真的能复现缺陷，而不是一条永远绿的假测试。
4. 作为 skill 维护者，我想要测试报告记录本次加载的 skill 内容指纹与 git rev，以便事后确认测的是哪一份 skill。
5. 作为 skill 维护者，我想要测试报告记录解析到的真实模型，以便模型换代后能判断历史结果是否可比。
6. 作为 skill 维护者，我想要被测 agent 只能看到用户原话和素材文件，以便测试结果反映真实用户场景而非我预先埋好的提示。
7. 作为 skill 维护者，我想要被测 agent 的工具面被限制为 `Skill`、`PowerShell`、`Read`、`Glob`、`Grep`、`Write`，以便它不能用 `WebFetch` 去查文档来绕过 skill。
8. 作为 skill 维护者，我想要每次会话在全新沙箱里运行，以便上一次的残留文件不会影响这一次。
9. 作为 skill 维护者，我想要沙箱里的 skill 是当前工作目录的那一份，以便在 worktree 里改的代码真的被测到。
10. 作为 skill 维护者，我想要沙箱只继承认证相关的环境变量，以便个人偏好（模型选择器、语言、更新器开关）不混进被测环境。
11. 作为 skill 维护者，我想要所有写入被限制在测试清单内，以便真实数据不会被误改。
12. 作为 skill 维护者，我想要越界写入被 shim 当场拒绝而不是事后发现，以便测试环境是安全的而不是靠信任。
13. 作为 skill 维护者，我想要被拒绝的调用留下记录，以便我知道 agent 曾经试图越界。
14. 作为 skill 维护者，我想要 harness 只删除自己创建的任务，以便清单里其他人建的数据不会被清掉。
15. 作为 skill 维护者，我想要断言只读本 run 的账本、完全不扫描清单，以便别人的任务永远不会污染判断，也不需要任何"清单是否干净"的检测机制。
16. 作为 skill 维护者，我想要失败的运行保留现场，以便我能回看 agent 到底做了什么。
17. 作为 skill 维护者，我想要一个显式的清理命令，以便确认完现场后一次性收尾。
18. 作为 skill 维护者，我想要会话的完整轨迹被原样保存，以便以后断言逻辑改了还能用同一份事实重放。
19. 作为 skill 维护者，我想要从 shim 拿到解析后的 argv 数组而非命令字符串，以便过程断言不用重新解析引号和转义。
20. 作为 skill 维护者，我想要可信度检查、过程断言、结局断言共同决定结果，以便"结局对了但绕远路"和"结果根本不可信"都被抓住。
21. 作为 skill 维护者，我想要过程断言只覆盖已确认的硬规则，以便"用了别的聪明做法"不会被误判。
22. 作为 skill 维护者，我想要判定 agent 对轨迹给出质量评价，以便看出绕路、冗余操作、没有先读后改这类问题。
23. 作为 skill 维护者，我想要判定 agent 不影响通过或失败，以便红绿信号不会随措辞漂移。
24. 作为 skill 维护者，我想要首次失败时自动重试一次，以便模型抽样波动不会淹没真实回归。
25. 作为 skill 维护者，我想要报告区分"正常完成"和"完成了但费劲"，以便从测试里读出 skill 质量的趋势。
26. 作为 skill 维护者，我想要每条 scenario 的成本与轮数被记录，以便发现异常昂贵的会话。
27. 作为 skill 维护者，我想要被杀的会话被判为"未收敛"而不是"失败"，以便诊断结论不被混淆。
28. 作为 skill 维护者，我想要 `npm test` 直接跑全量，以便 `/implement` 的"full test suite"自动命中。
29. 作为 skill 维护者，我想要 `/tdd` 写红测试时先加 scenario 再跑它，以便红绿循环和现有工作流一致。
30. 作为 skill 维护者，我想要 scenario 的断言基于实测行为而非反馈原文的描述，以便断言不会建立在不成立的前提上。
31. 作为 skill 维护者，我想要新增 scenario 时能先跑一次只带原话、不带断言的会话拿到事实样本，以便断言写在实际发生的行为上而不是我的想象上。
32. 作为 skill 维护者，我想要一个人工复核清单，以便验证"客户端是否渲染正文"这类无法自动化的判断。
33. 作为 skill 维护者，我想要网络失败的 scenario，以便验证 skill 是否教 agent 正确处理不可重试的错误。
34. 作为 skill 维护者，我想要 harness 在清单里出现非本 run 创建的任务时完全不检测、不报告，以便运行路径里没有只为兜住代码 bug 而存在的机制。
35. 作为 skill 维护者，我想要硬规则：清场永不按清单扫描删除，以便这次误删他人任务的事故不会重演。
36. 作为 skill 维护者，我想要一条 scenario 需要前置数据时，能在会话前用真 CLI 建好任务，以便测试"查任务""改任务"这类必须已有数据的场景，而不必造一条依赖上一条的链式用例。
37. 作为 skill 维护者，我想要预设建的任务和被测 agent 建的任务进同一份账本，以便清场与 `--clean` 都能管到它们，不留残渣。
38. 作为 skill 维护者，我想要预设用的是本次运行实际在用的清单、并且越界时被当场拒绝，以便写错清单不会静默建出清场删不掉的孤儿任务。
39. 作为 skill 维护者，我想要结局断言以模块形式放在用例目录里，以便加一条 scenario 只是加一个目录，harness 一行不改。
40. 作为 skill 维护者，我想要断言返回一组带期望值与实际值的结果而不是抛第一条异常，以便一次跑出所有失败项，不用修一条跑一条。
41. 作为 skill 维护者，我想要断言按字段定位任务而不是按顺序猜，以便被测 agent 建了几条、以什么顺序建都不影响判断。
42. 作为 skill 维护者，我想要账本条目标明这条任务是预设建的还是被测 agent 建的，以便断言能只针对其中一类。
43. 作为 skill 维护者，我想要会话结束后的任务现状落盘成终态快照，以便断言逻辑改了之后能用同一份事实重放，不必重新烧 API。
44. 作为 skill 维护者，我想要发现被测 agent 绕过 shim 时该次运行被判为"结果不可信"而不是"失败"，以便偶发的绕过不会污染红绿信号、被误当成 skill 缺陷。
45. 作为 skill 维护者，我想要探针放在与正式用例分开的目录里，以便肉眼就能看出有没有忘记清理的探针。
46. 作为 skill 维护者，我想要正式用例缺断言时直接报错而不是跳过，以便漏写或误删的 `assert.mjs` 不会让回归网静默少一条、退出码却仍是 0。

## Implementation Decisions

### 结构与职责

harness 是仓库根目录下的一个 Node 模块目录，入口是一个可执行脚本，无第三方框架依赖。用例数据放在另一个目录，与 harness 分开——harness 是机器，用例是数据。

- **编排器**：串联预设 → 建沙箱 → 起会话 → 落产物 → 三面判定 → 清场。开跑前不做任何清单检查。
- **沙箱模块**：建临时目录、复制 skill、算指纹、生成配置。它只为被测 agent 服务，预设与断言都在它之外。
- **会话模块**：拼装并启动 `claude -p`、清理继承的环境变量、解析 NDJSON。
- **断言装配**：加载用例目录里的结局断言模块，算出终态快照，收集三面结果。
- **判定模块**：起判定 agent、写质量报告与人工复核表。不影响退出码。
- **shim**：`dida.cmd` + 一个 Node 脚本承担判定与记账。

### 用例目录

```
skill-tests/
├── scenarios/<id>/
│   ├── scenario.json      # 原话
│   ├── materials/         # 可选，给被测 agent 读
│   ├── preset.mjs         # 可选，声明要建的任务
│   └── assert.mjs         # 结局断言
├── probes/<id>/           # 探针，跑完即删
└── README.md              # 写用例的流程
```

`skill-tests/` 而非 `tests/`：避免与 harness 自己的单元测试混淆。

**原话**是 `scenario.json` 的唯一字段，也是被测 agent 唯一的文本输入。约束：

- 可以且必须点名测试清单。写命令的 `--project` 必填且目标必须 ∈ 测试清单集合，不点名会被 shim 全拒，那条 scenario 就是假红。
- 不得出现"测试""评测""断言""期望"字样，不得写出期望结果，不得包含反馈原文。

**素材**是原话里要引用的文件，整体复制进沙箱。它是给被测 agent 读的。

**预设**在建沙箱之前由 harness 用真 CLI 执行，不经 shim。建出的 id 立刻写进本 run 的同一份账本。预设只造数据结构，不造语义提示——它建的东西被测 agent 看得到。预设从 harness 拿到本次 run 的清单而不是仓库默认常量；校验规则（含指向任务的参数一律拒绝）见 ADR-0012。

**断言**是模块，默认导出：

```js
// 出自实现前的设计约定，不是原型产物
({ tasks, created, calls, session }) => { ok, name, expected, actual }[]
```

- 空数组即通过。返回数组而非抛异常，一次跑出所有失败项。
- `tasks` 是终态快照：账本里每个 id 取回的任务对象，取不到的记 `null`。按测试清单枚举定位，枚举不到才回退账本的 `projectId`。
- `created` 是账本条目，带 `origin: 'preset' | 'agent'`。
- `calls` 是调用日志的解析结果。
- `session` 是退出码、超时、轮数、成本。
- 断言按字段定位任务，不按顺序猜。

**探针**是没写断言的用例，放在单独目录，不参与全量判定。跑完产出轨迹、调用日志与终态快照供人写断言，然后删掉。

反过来，**正式用例缺断言时直接报错退出，不跑会话**。两个目录的区分就是「有没有断言」——跳过会让漏写或误删断言的用例静默退出回归网，而退出码仍是 0。这是**三面之外的前置失败**：报告里单列「用例配置错误」，与「断言未通过」并列。

### 三面判定

| 顺序 | 面 | 读什么 | 失败含义 | 作用域 |
|---|---|---|---|---|
| 1 | 可信度检查 | 调用日志条数与轨迹里的命令调用数 | 结果不可归因，标 `invalid` | harness 全局 |
| 2 | 过程断言 | 调用日志的 argv 序列 | 做到了但绕路，标 `fail` | harness 全局 |
| 3 | 结局断言 | 终态快照 | 见下：`fail` / `broken` / `invalid` | 每条 scenario |

任一面红即停，退出码非零。报告写明是哪一面、哪条断言、期望值与实际值。

结局断言这一面内部再分三种：断言跑完且有失败项标 `fail`（skill 没做到）；断言模块没给出合法结果标 `broken`（用例有缺陷）；终态快照取不到标 `invalid`（结果不可归因，重跑）。见 ADR-0012 的「补充：结局断言阶段的三类失败」。

**可信度失败标 `invalid` 而非 `fail`**：退出码同样是 1，但语义是"重跑"，不是"skill 有缺陷"。区分它们是为了让红绿循环不被偶发的绕过污染。

过程断言只读调用日志，不读轨迹。轨迹只服务于可信度检查。

### 预设的时序

```
预设（真 CLI，直接打真实清单）
  → 建沙箱 → 起会话 → 落产物
  → 可信度检查 → 过程断言 → 结局断言
  → 清场
```

预设不依赖沙箱：它只需要本次 run 的清单、`runId` 与账本路径，这三样在建沙箱之前就确定。排在最前也意味着预设失败时不必浪费一次建沙箱。

预设建出的任务与 shim 记的走同一份账本。若另起一套记录，按"只认账本"的规则它们就永远清不掉。

不做链式 scenario（一条建、另一条查）：账本按 runId 隔离，后半条既断言不了也清不掉前半条的数据；单跑一条也必然缺前置数据。

### 会话启动契约

- 用 `--agents` 加载一份工具面受限的 agent 定义，用 `--agent` 选中它。实测 `--agent` 与 `--tools` 都能限制工具，选 `--agents` 是因为定义是仓库里的文件，有 diff、能 review、能回滚，且开机成本更低。
- 必须同时传 `--allowedTools`。实测只给 `--agents` 限制工具而不给 `--allowedTools`，所有命令都会被 `dontAsk` 模式拒绝。
- 必须重定向 stdin。实测 stdin 未关闭时 `claude -p` 会等待输入并挂死，表现为超时且无任何 `result` 输出。
- 输出用 `--output-format stream-json --verbose`，`--no-session-persistence` 避免落在用户目录。
- 权限模式用 `dontAsk`。

### 隔离

- 沙箱是每次运行新建的临时目录，含 skill 副本、素材文件、只含 `ANTHROPIC_*` 键的 `settings.json`、以及 shim。
- 会话以沙箱目录为 `cwd`、以沙箱配置目录为 `CLAUDE_CONFIG_DIR` 启动，并清除从父进程继承的全部以 `CLAUDE` 开头的环境变量。CLI 自身注入的变量不受此控制。
- 沙箱**不放仓库内**：放在仓库子目录会继承父目录的 `CLAUDE.md` 与父目录 `.claude/skills/` 下的 skill，后者的同名 skill 会与沙箱副本竞争。
- 沙箱路径写入 manifest 并打印在报告首行；运行失败时不删除沙箱，便于回看现场。
- **沙箱只隔离工作目录，不隔离文件系统**：被测 agent 仍可用绝对路径读取沙箱外的任何文件，包括本机凭据。这是一个已知且尚未缓解的风险，`runs/` 因此在脱敏方案定下来之前不得进入版本控制。

### shim 规则

单份 `dida.cmd`，判定与记账后原样转发给真 CLI，退出码透传。

**一条规则：解析不出目标，或目标不在测试清单集合内，就拒绝。** 没有可判定目标的写命令（`project create`、`project group *`、`habit *`、`focus *`、`tag *`、`auth login/logout/token`）同样拒绝，不默认放行。

- `task update` 的定位键是 `--id`，`--project` 只写进 `projectId`；两者不一致时要求位置参数与 `--id` 相同，否则拒绝。
- `task complete-batch` 的 `--project` 是**可选**参数，省略时写进收集箱，因此缺省必须拒绝。
- 拒绝时输出与真 CLI 同构的 API 错误文本与退出码 1，不暴露测试机制。
- 测试清单集合在生成沙箱时烘焙进沙箱配置，**不从环境变量读**：被测 agent 能读能改进程环境，从 env 读白名单等于把判定权交给它。
- **这个防护不是只读的**：配置文件在沙箱内，被测 agent 的工具面里有 `Write`，可以覆写后让 shim 放行。要真正堵住需要把白名单放到 agent 写不到的位置，与"沙箱不隔离文件系统"同源。

### 测试清单

`Test_1` 与 `Test_2` 两个清单。id 以仓库里的常量作为默认值，可用环境变量覆盖；覆盖成空值退回默认——一次运行没有测试清单是不可用的状态。当前两者均为空。

### 报告

每次运行产出：manifest（skill 指纹、git rev、沙箱绝对路径、三层模型信息、成本、轮数）、原始轨迹、调用日志、账本、终态快照、断言结果、质量报告、人工复核表。产物写在仓库根的 `runs/` 下，`runs/` 进 `.gitignore`。

运行失败时保留沙箱与产物不删。通过或失败只由三面判定决定，质量报告不影响退出码。

### 模型记录

记录三层并标注可信度：CLI 自报的别名、从 `ANTHROPIC_DEFAULT_*` 读到的真实映射、代理地址。CLI 自报的模型名是别名，不可作为实际执行的模型凭据。

### 护栏

`--max-turns` 在本机 CLI 上被接受但无效，轮数限制必须由 harness 侧看门狗实现，超出阈值直接杀进程树并判"未收敛"。`--max-budget-usd` 是硬中断但会超支约一个调用，且中转账单与本地估算存在出入，只作量级参考。护栏是第二阶段的事。

## Testing Decisions

### 什么是好测试

只测外部行为：会话结束后测试清单的实际状态，以及这次会话真实发生过的调用。不断言 harness 内部实现，不断言 skill 文件的具体措辞——改写法不该让测试失败，改行为才该。

### 唯一接缝

一条 scenario 的接缝是**一次完整的 agent 会话**。所有判断都从三个事实源读取：会话结束后测试清单的最终状态（经账本限定）、该会话的调用日志、该会话的轨迹。

不建 CLI 层的独立接缝：那里的断言测的是 npm 包，改 skill 永远不会让它变绿。不建 shim 层的接缝：它是基础设施，不是被测对象。

loading 断言模块与计算终态快照不是新接缝——它们是数据装配，不是被测对象。

### 断言构成

- 可信度检查：调用日志条数与轨迹里的命令调用数的比对。
- 过程断言：调用序列上的硬规则，当前只有三类（不得先建 `CHECKLIST` 再删掉重建、不得让 `content` 从非空变空、不得有越界写入）。
- 结局断言：账本里那几条任务的终态字段判断。

三者共同决定通过或失败，按顺序短路。

### 已知的判据局限

- 可信度检查的现判据只比**条数**，抓不到"3 次命令调用里 1 次绕过、另 2 次各跑 2 条 dida"这种总数反多的情况。要真正抓住需要逐调用比对命令内容。
- 过程断言第二条（`content` 从非空变空）依赖 `--content` 的完整参数。当前经 `.cmd` 形态时多行 `--content` 会被截成第一行，这条规则的判据会失真。

### scenario 的取材

新增 scenario 必须先在探针模式下跑一次真实会话，拿到事实样本后写断言。不得从缺陷报告的文字描述直接反推断言——事实核验阶段已经发现，报告中"更新会清空正文"这条在当前版本上不成立。

### 先行验证过的事实

事实核验阶段与后续实测确认了以下行为，scenario 的断言以此为准：

- `--items '["A","B","C"]'`（字符串数组）会逐项被丢弃并告警，任务落成 `TEXT` 且 `items` 为空；只有对象数组 `[{"title":"A","status":0}]` 或逗号分隔才生效
- 用对象数组建成的任务 `kind` 为 `CHECKLIST`，同时 `content` 可以非空——数据存在但客户端不渲染
- `create --items` 建的是检查事项，父任务变 `CHECKLIST`，`items[]` 有值
- `create --parent-id` 建的是真子任务，父任务保持 `TEXT`，`childIds[]` 有值
- `update --items` **不会**清空 `content`
- `update --items ""` 完全无效，`items` 保留，`kind` 无法回退
- `task get --json` 遇 404 时 stdout 为空，错误以纯文本落在 stderr，进程以非零退出码崩溃
- 只写 `--content` 建成 `TEXT`，再用 `--parent-id` 建子任务，父任务保持 `TEXT`、`content` 不变、`childIds` 正确
- 任务对象含 `id`、`projectId`、`title`、`content`、`kind`、`status`、`items[]`、`childIds[]`、`priority`、`dueDate`、`completedTime` 等字段；`kind` 为 `TEXT` 的任务没有 `items`，`childIds` 只在有子任务时出现
- 空清单时 `task filter --json` 的 stdout 是空串

## Out of Scope

- 修改 `dida` 二进制本身。它不在本仓库，六条缺陷中的 CLI 层问题只能通过 skill 文档规避，无法修复。
- 自动验证滴答客户端的渲染结果。客户端不提供可编程接口，只能靠人工复核表。
- 跨平台支持。harness 绑定当前 Windows 环境的具体行为（`PowerShell` 工具、`.cmd` 形态、无 OS sandbox）。
- 通过网络层面模拟 `fetch failed`。shim 可以注入该故障，但属于第二阶段。
- 轮数看门狗与预算护栏。已确认 `--max-turns` 无效、预算护栏会超支且金额不可信，具体实现留到第二阶段。
- 判定 agent 的评分纳入通过标准。它只写报告。
- 在 CI 中运行。会话成本与对本地登录态的依赖决定了它只能在维护者本机跑。
- 链式 scenario（一条建数据、另一条查数据）。需要前置数据时用预设。
- 完全隔离被测 agent 的文件系统读取。当前工具面含 `PowerShell` 时无法做到，风险与已失效的缓解手段单独跟踪。

## Further Notes

- 一次极短会话的固定成本约 $0.03–0.09（系统提示与工具定义的开销），14 轮文件操作约 $0.29。工具面收窄能显著降低成本。成本数字来自本地估算，中转账单可能不同。
- `~/.claude/settings.json` 把四个模型别名全部映射到中转站的模型，因此 CLI 报告的模型名与实际执行的模型不是一回事。
- 事实核验期间发生过一次数据事故：清理探针任务时按清单全量删除，误删了用户手动创建的一条任务，且 Open API 无回收站可恢复。这条事故直接产生了清场只认账本的硬规则与第 14、15、34、35 条用户故事；其中 15 与 34 后来按修订后的模型改写。
- 用户故事 15 与 34 曾在早期版本里要求"运行前检查清单是否为空""发现非本 run 任务就停下"。这两条已作废：它们建立在"断言要扫描清单才能找到任务"的错误假设上，而断言实际从账本读 id。作废的经过见 ADR-0010。
- 相关决策见 `docs/adr/` 下的 ADR-0001 至 ADR-0012。
